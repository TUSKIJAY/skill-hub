# readable-docs

本 skill 让 agent 写给人看的文字更好读。规则有两套：

- **编号可读**：任务、决策、账本条目、提交等编号第一次出现时，括号里带一句说明。说明取自原始记录。
- **中文句式**：一句只说一件事，不用分号串几件事，术语首次定义，不改情态，不补事实。

本 skill 只放机制和通用规则。项目里的事实由 install 审计得出，经用户确认后存进项目。这些事实包括：有哪些编号种类、去哪查说明、哪些词不是同义词、规则卡放哪。

把这个目录记作 `SKILL_ROOT`。命令里的 `python` 指项目里核实过的解释器。

## 什么时候用

- 用户要给一个项目接入写作规则。
- 用户要把旧文档改得好读。
- skill 版本更新后，要把新规则合进已接入的项目。
- 用户给出一段难懂的中文，要求改写。

日常写方案、计划、汇报时不需要调用本 skill：项目启动文件里的规则卡已经写明要点。

不用于代码、配置、账本和命令输出，也不用于创意、营销和需要语气的文字。

## 核心规则

完整规则见 [rules/id-glossing.md](rules/id-glossing.md) 和 [rules/zh.md](rules/zh.md)。要点：

1. 编号第一次出现时，括号里带一句说明，例如 `TASK-003（SD 卡挂载）`。
2. 说明必须来自原始记录：任务卡标题、决策标题、账本摘要、提交信息。查不到就写"未查到"，不能凭印象补。
3. 编号只作句末证据出处时，可以不带说明，例如"模板已合并（`e2c366`）。"。
4. 不连串堆叠没有说明的编号。
5. 一句只说一件事。不用分号串几件事。三步或三个条件以上用列表。
6. 术语第一次出现时给一句定义。
7. 不改情态。"可能""尚不能判定"不能写成事实。
8. 不补原文没有的事实，不删条件和范围。
9. 给用户审的方案和计划，开头写摘要：要做什么、为什么、改哪些、风险、要用户决定什么。

## install：接入一个项目

1. **审计（只读）。**

   ```sh
   python "<SKILL_ROOT>/scripts/audit.py" --target <project> --draft-out <项目外的临时路径>
   ```

   审计输出以下内容，其中 `config_draft` 是配置草稿：
   - 项目形态，以及规则卡写到哪个文件。
   - 编号命中情况和未登记的编号形状。
   - 可能不是同义词的词组。
   - 文档模板候选和冻结目录候选。

   audit 不往项目里写：`--draft-out` 指向项目里的路径或已有文件时，直接报错退出。

2. **和用户确认配置草稿。** 逐项确认：
   - `id_kinds`：编号种类和查说明的地方。未登记形状里，项目真在用的编号要加进来。
   - `terms.distinct`：在本项目是不同概念的词组，例如"用户"和"客户"。
   - `terms.allow`：在本项目不算营销词或含糊词的词，例如治理用语"闭环"。
   - `frozen`：转换时不动的文件，例如已完成计划、迁入原件。
   - `rules`：每条规则的档位（`warn`、`block`、`off`）。默认全部 `warn`。
   - `templates`：要加"给审阅人的摘要"的文档模板。
   - `card`：规则卡里的适用范围和编号示例。示例的说明也要来自原始记录。

3. **预览。**

   ```sh
   python "<SKILL_ROOT>/scripts/apply.py" --target <project> --config <确认后的配置>
   ```

4. **用户同意预览后写入。** 同一命令加 `--apply`。apply 只做三种写入：新建缺少的文件、追加带标记的一节、插入一行。它从不覆盖已有文件。另有三条保护：
   - 写入路径必须在项目里。模板或 `--check-path` 指向项目外时，apply 拒绝整次写入。
   - 配置已存在时不覆盖。规则卡和模板按已装的配置渲染。和这次给的配置不同时，标成 `manual-merge`，请手工合并。
   - 有未提交改动的文件会拦住整次写入，确认后才能加 `--allow-dirty`。

   规则卡放哪：

   | 项目形态 | 规则卡位置 |
   | --- | --- |
   | 完整 harness：AGENTS、INSTRUCTIONS、`.harness/config.json` | `INSTRUCTIONS.md` 末尾新增一节，检查命令加进 `.harness/config.json` |
   | 有 AGENTS 和 INSTRUCTIONS | `INSTRUCTIONS.md` 末尾新增一节 |
   | 只有 AGENTS，或 AGENTS 加 CLAUDE.md | `AGENTS.md` 末尾新增一节，CLAUDE.md 不重复写 |
   | 只有 CLAUDE.md | `CLAUDE.md` 末尾新增一节 |
   | 没有指令文件 | 不写。用户同意后先建一个最小的 AGENTS.md |

   非 Git 项目没有改动行可比。规则卡里的检查命令写成 `--files <改过的文件>`，harness 的验证命令写成 `--report`。提交号的查法标成手工，因为项目里没有 `git log` 可查。

5. **收尾。** 按 apply 输出的 `next_steps` 做：
   - 跑一次 `--report` 看基线。
   - harness 项目按其规则记账本、同步状态文件、登记决定。
   - 跑项目自己的检查，再按项目的规矩提交。

   写进启动文件属于该项目的 harness 维护，要有用户授权。

## convert：转换旧文档

分三级：

| 级别 | 做什么 | 适用文档 |
| --- | --- | --- |
| A：只加编号说明 | 对照原始记录补说明 | 所有给人看的文档，包括已生效的决策和已确认的需求 |
| B：A 加改句式 | 拆句、改列表、补术语定义 | 待用户审的方案、计划、评审回复、研究报告 |
| 冻结 | 不动 | 配置里 `frozen` 列出的文件 |

每篇的步骤：

1. 跑 `python scripts/check-readable-docs.py --files <文档>`，记下转换前的发现数和字符数。
2. 列出文中的编号，按配置逐个查原始记录，写出说明。查不到写"未查到"。
3. 只有 B 级才改句式。不改情态，不补事实，不删条件和范围。
4. 发现的歧义列成问题交给用户，不自己猜。例如同一编号指向不明，或引用的章节查不到。
5. 再跑一次检查，记下发现数和字符增量。
6. 给用户看 diff。用户确认后，按项目的规矩提交。

约束：

- 已生效的决策和已确认的需求只做 A 级。改它们的句式等于改规则原文，要用户确认措辞。
- 用户原话、代码块、命令和日志不改。
- 每批建议不超过 5 篇，每批一个提交。
- 有篇幅上限的状态文件（例如 PROGRESS），先按项目的归档流程腾出空间，或者只对新写的条目照做。

## upgrade：升级已接入的项目

1. 跑 audit，看 `existing.check_script` 里的版本，和本 skill 的版本对比。
2. 检查脚本有差异时，用 `git diff --no-index <项目里的脚本> "<SKILL_ROOT>/scripts/check.py"` 给用户看差异。用户同意后再替换。
3. 规则卡的标记里带版本号（`<!-- readable-docs:rule-card v0.1.1 -->`）。版本不同时，把新旧规则卡的差异给用户看，同意后只替换这一节。
4. 配置有新字段时，列给用户，确认后手工合并。

## rewrite：改写一段文字

1. 先读懂原文，弄清改完必须保留什么。
2. 按 [rules/zh.md](rules/zh.md) 的扫描清单逐句检查。
3. 改写。编号按 [rules/id-glossing.md](rules/id-glossing.md) 补说明。
4. 默认只给改写后的正文。用户要看改动时，给"违反的规则 / 原文 / 改写后"的表。
5. 原文已经清楚，就直说，不硬改。

## 边界

- 不把项目里的事实写进本 skill。
- 不整份覆盖已有文件，不删除用户文件。
- 不推送，不对外发送。
- 遵守项目自己的授权、泄漏扫描和提交规则。
- 检查脚本只做机械检查。零发现不代表写得好，也证明不了说明和原始记录一致。

## 资源

- `scripts/audit.py`：只读审计，输出配置草稿。
- `scripts/apply.py`：预览和写入，从不覆盖。
- `scripts/check.py`：检查脚本，安装时拷成项目的 `scripts/check-readable-docs.py`。单文件，只用标准库，Python 3.9 以上。
- `assets/rule-card.zh.md`：规则卡模板。
- `assets/template-summary.zh.md`：给文档模板加的摘要片段。
- `assets/readable-docs.json.tmpl`：配置字段的完整示例。
- `rules/`：规则全文。
- `tests/`：本 skill 的回归测试，不装进项目。运行：`python -m unittest discover -s "<SKILL_ROOT>/tests" -p "test_*.py"`。
- `NOTICE.md`：来源和许可。
