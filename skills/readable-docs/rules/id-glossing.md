# 编号可读

## 目标

读者只看到编号，不知道它指什么。编号第一次出现时，旁边带一句说明，读者不用去查原文也能看懂。

## 适用范围

- **适用**：给人看的文字，包括汇报、方案和计划正文、交接文件、状态说明、评审意见、计划讲解。
- **不适用**：机器读写的数据，包括账本、配置、代码，以及代码块里的命令和日志。

## 规则

1. **第一次出现时加说明。** 编号在同一份文字里第一次出现，括号里紧跟一句说明。后面再出现可以只写编号。
   - 写法：`` `d4f31a`（DSP 方案对齐 harness）``、`TASK-003（SD 卡挂载）`、`[D0033](decisions/0033.md)（讨论期产物入 Git）`。
   - 说明约 15 个汉字，写"做了什么"或"要达成什么"，不写过程。
2. **说明必须来自原始记录。** 来源是任务卡标题、决策标题、账本摘要或提交信息。查不到就写"未查到"，不能凭印象补。
3. **不连串堆叠编号。** 不写"见 `a1`、`b2`、`c3`"，要写成"见 `a1`（批准合并）、`b2`（合并完成）、`c3`（安装）"。
4. **证据出处可以不加说明。** 前面的句子已经说清事实，编号只放在句末括号里作出处时，不必再加。例如"主方案已对齐 harness（`d4f31a`）。"。
5. **定义处不用加说明。** 标题、表格首列、列表标签里的编号就是在定义它，例如 `### 待决3 停止本地下载`。
6. **新建文件时，文件名用"编号-短标题"。** 例如 `TASK-003-sd-card-mount.md`、`0007-use-postgres.md`。
7. **引用别的文档里的编号时，带上来源。** 不同文档可能用同一个编号。写成"迁移计划的 TASK-003（SD 卡挂载）"，不只写编号。

## 去哪查说明

查找途径由项目配置的 `id_kinds[].lookup` 给出。常见的有：

| 编号种类 | 去哪查 |
| --- | --- |
| 提交哈希 | `git log -1 --format=%s <hash>` |
| harness 账本条目 | `scripts/harness_log.py show --id <id>`，旧版没有 `show` 时用 `query --grep <id>` |
| 决策 | 决策索引表的标题列，或决策文件的一级标题 |
| 任务卡、计划 | 文件一级标题，或索引表的标题列 |

同一种写法可能对应多个来源，例如 12 位十六进制可能是账本条目，也可能是提交。按配置里的顺序逐个查。

## 检查脚本能查什么

- `bare-id-run`：同一行两个以上编号之间只有分隔符，没有说明。
- `first-mention`：已登记的编号第一次出现时，后面没有括号说明。
- `unregistered-id`：像编号，但不在配置里。

脚本只认括号形式的说明，也查不出说明和记录是否一致。说明对不对，要人或 agent 对照记录核实。

## 依据

- GitHub Spec Kit：任务模板规定每个任务写成"编号加描述"。
- OpenAI ExecPlans：计划要自包含，术语用平白的话定义。
- GitLab：`#123+` 引用在显示时展开成标题。
- ADR、Rust RFC、KEP：文件名用"编号-短标题"。
