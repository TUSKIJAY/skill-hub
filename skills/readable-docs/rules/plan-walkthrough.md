# 计划讲解

## 目标

计划文件可以只写给 agent 看：密、带编号、带阶段闸门。拍板的人不必读这份文件。给人评审时，由 agent 把计划讲给他听。讲解就是人参与评审的方式。没有人真正看过、也没有人明确选择跳过的计划，不算评审过。

## 适用范围

- **适用**：用户要求讲解的计划，随时讲。项目流程要求先问、用户选择听的计划，例如 harness 项目评审通过后、激活前。
- **不适用**：用户明确选择跳过讲解的计划。用户明确请求、直接执行的小改动。

什么时候必须问、什么时候可以跳过，由项目的计划流程规定。harness 项目见 `docs/exec-plans/roadmap.md`。

## 先问再讲

流程要求先问的场合，问句附三样：

1. 摘要：要做什么、为什么、改哪些、风险、要用户决定什么。
2. 每个待拍板项一句话，加建议。
3. 一个问题："要听一遍讲解，还是跳过直接批准？"

用户要听，第一块就是这份摘要，然后按下面的规则往下讲。用户跳过，就不讲。待拍板项按建议办，并记下这是用户跳过的。用户没有答复，不算跳过。

## 规则

1. **一次讲一块。** 块按内容分。常见的分法：这个计划做什么和不做什么、用户要做什么、关键规则和取舍、每个待拍板项。
2. **顺序由 agent 定。** 按怎么讲最清楚来排，不必照文件章节。agent 可以按自己的理解重组材料。
3. **每块讲完问一个具体问题。** 等人回应再讲下一块。问题要能直接回答，例如"这条边界你接受吗"。不问"有没有问题"。
4. **每个待拍板项讲清四点。** 是什么、建议选哪个、为什么、另一个选择的代价。
5. **每个改动都要讲到。** 修订稿要说清改了哪里、为什么改。评审意见里哪些采纳了、哪些没采纳，也要说。
6. **编号第一次出现时说明它是什么。** 写法同 [id-glossing.md](id-glossing.md)。
7. **用人话讲。** 句式按 [zh.md](zh.md) 的顺畅档。计划文件里的术语和缩写，讲的时候展开。

## 不做的事

- 不把整份计划贴给用户代替讲解。
- 不一次问好几个问题。
- 不在用户答复前把建议写成已定。
- 不把用户的沉默当成跳过。
