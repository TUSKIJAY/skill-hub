# 中文句式规则

读者是没有机会追问的另一方：另一个 agent、审方案的人、半年后的自己。目标是让他读不错。

规则的分类思路来自 ste-zh（ASD-STE100 的中文对应物，MIT 许可，见 NOTICE.md）。这里按本 skill 的用途重新写过。

## 两档

改写前先选档。用户没说时按文本类型判断。

- **严格档**：程序步骤、报错信息、工具描述、给 agent 的指令、涉及安全的文字。全部规则都执行，指令句不超过 25 字。
- **顺畅档**：方案、计划、README、PR 说明、研究报告。结构规则全执行，用词规则只作方向，句子不超过 40 字。

检查脚本分不出指令句和说明句，只按说明句上限（配置里的 `max_chars.explanation`）查句长。指令句的 25 字上限靠改写时自己把握。

## 结构规则

<!-- readable-docs:off -->
| 规则 | 这样写 | 不要这样写 |
| --- | --- | --- |
| 主动语态 | 脚本删除临时文件。 | 临时文件被脚本删除。施事未知或无关时才用"被"。 |
| 一句一件事 | 打开文件。读第 3 行。 | 打开文件并读第 3 行，然后检查是否匹配。 |
| 句长 | 指令句不超过 25 字，说明句不超过 40 字 | 一句话套三层 |
| 不用分号串事 | 拆成两句 | "先做 A；再做 B" |
| 不省略成分 | 未备份的文件会丢失。 | 文件未备份将丢失。（哪些文件？） |
| 保留情态 | "请求可能已失败"照写 | 把"可能"升成事实 |
| 段落 | 一段一个主题，不超过 6 句 | 一段塞三件事 |
| 列表 | 三步或三个条件以上用列表 | 把步骤塞进一句 |

## 用词方向

<!-- readable-docs:off -->
| 规则 | 这样写 | 不要这样写 |
| --- | --- | --- |
| 一词一义 | 同一个动作全篇用同一个词 | 检查、校验、核对轮着用 |
| 动词优先 | 分析日志。 | 对日志进行分析。 |
| 去营销词 | 删掉，或换成能证明的说法 | 无缝、强大、赋能、极致、一站式 |
| 术语首次定义 | 第一次出现时给一句定义 | 直接用黑话 |
| 具体化 | 3 秒内重试 2 次 | 快速重试若干次 |
<!-- readable-docs:on -->

一词一义有例外：项目里本来就不同的两个概念，不能为了统一用词而合并。例如"用户"指操作系统的人，"客户"指下订单的公司。这类词组写进项目配置的 `terms.distinct`。

## 体貌

<!-- readable-docs:off -->
中文没有时态，但"已经……了""正在……中"带有信息。默认用简单说法，"任务已结束"可以写成"任务结束"。表达当前状态时要保留："任务已完成，结果可以直接读"和"任务完成过"不是一回事。
<!-- readable-docs:on -->

## 扫描清单

改写前把六项都扫一遍。每一项都能指出具体的词或标点。

<!-- readable-docs:off -->
1. **同义轮换**：同一件事换了几个名字。定一个名字，全篇用它。
2. **套话**：需要注意的是、值得一提的是、在一定程度上。删掉，直接说事。
3. **名词化**：进行、作出、加以、予以加名词。改成动词。
4. **营销词**：无缝、强大、赋能、极致、一站式。删掉，或换成能证明的说法。
5. **长句串联**：用分号、破折号、"并且、同时、从而"串好几件事。一句一件事。
6. **翻译腔**：基于……的情况下、对于……而言。说清主语和动作。
<!-- readable-docs:on -->

## 改写流程

1. 选档。
2. 通读原文，弄清改完必须保留什么。没读懂不动笔。
3. 逐句对照结构规则、用词方向和扫描清单，标出问题。
4. 改写。原意一个字不能变。
   - 先看情态。"可能、也许、有时"是作者的置信度，是内容。删掉它就换了结论。
   - 不补原文没有的事实。改完读着更顺，往往是因为补了原因或频率，那已经不是改写。
   - 改短会丢掉必要的条件、范围或数字时，保留长写法，并在正文后加一行"保留原样："说明。
5. 默认只给改写后的正文。用户要看改动时，给"违反的规则 / 原文 / 改写后"的表。
6. 原文已经清楚，就直说，不硬改。

## 不做的事

- 不声称符合某个官方中文受控词表。中文没有这样的标准。
- 不改写创意、营销和需要语气的文字。
- 不为了短而删掉安全条件、例外和范围。
- 不把空内容改成有用的内容。空话改完还是空话，要直说。
